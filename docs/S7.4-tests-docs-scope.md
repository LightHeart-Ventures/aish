# S7.4 / TASK-142 — Tests + docs; bound the scope (no pipeline engine)

S7 gives an aish tool a second, *typed* voice. Alongside the human-readable
`content` string a tool may attach an **optional** structured payload: the model
reasons over it as trustworthy JSON, the human inspects the verbatim text raw
(Ctrl-O). S7.4 is the sprint's closing card — it makes that capability
**trustworthy** (tests pin both result paths) and **bounded** (a written
guardrail stops the feature sliding into a structured-pipeline engine).

This document is both the S7.4 PRD and the durable scope guardrail the
`ToolResult` definition points back to (`src/backend/mod.rs`). §3 is the
load-bearing section: a reviewer must be able to state the boundary from it.

---

## 1. Background — where S7 landed

| Slice | Card | What it added |
|-------|------|---------------|
| S7.2 | TASK-140 | Optional typed payload on `backend::ToolResult` (`structured: Option<Value>`); `ToolResult::text` / `ToolResult::structured` constructors. `content` stays the rendered, human-readable source of truth. |
| S7.3 | TASK-141 | `ToolResult::model_content()` — the single model-facing representation (compact JSON when a payload is present, else `content` verbatim); both backend renderers thread it; `engine::raw_body` (Ctrl-O) stays on `content` with a structured-only pretty-JSON fallback. |
| **S7.4** | **TASK-142** | **This card** — tests pinning both paths + this scope guardrail + the code pointer + a CHANGELOG note. No new runtime surface. |

The two result paths that now exist and must both keep working:

- **String-only path** — `structured == None`. Every tool took this before S7.2
  and every text-only tool still does. The backend wire block carries `content`
  verbatim and **no** payload key; `is_error` is honoured.
- **Structured path** — `structured == Some(payload)`. The model receives the
  compact JSON via `model_content()`; the human still sees the verbatim
  `content` raw (Ctrl-O). The payload is **additive** — it never mutates or
  substitutes `content` or `is_error`.

---

## 2. Problem

Two risks were left open after S7.3:

1. **Correctness is unpinned.** Two result paths (string-only vs structured)
   with nothing guaranteeing both keep working through the backend render, the
   model-facing representation, and the Ctrl-O raw path. A refactor could
   silently start serializing the payload as a wire sibling of `content`, or
   substitute the JSON for the human's raw view, with no test to catch it.
2. **Scope is undefined.** "Tools return structured data" sits one inch from
   "add operators to filter / transform / compose those outputs" — i.e.
   reinventing a shell **pipeline / query engine** inside aish. That is an
   explicit non-goal (`aish-next.md` §3.4): aish routes a line to a real shell
   or to the model; it is not itself a typed dataflow runtime.

## 3. Scope guardrail — the boundary (load-bearing)

**aish tool results may DESCRIBE their output in a typed way. aish must never
OPERATE on those types as a programmable pipeline.**

A typed payload is a *passive, per-call, opaque* attachment for the model to
read. It is not a value in a dataflow graph.

### In scope (what S7 is)
- A tool MAY attach one optional structured payload describing its already-
  rendered result (records / tables): `list_dir`, `glob_expand`, `grep_files`,
  `stat_file`, `diff_files`, and MCP JSON passthrough.
- The payload is **additive**: `content` remains the human-readable source of
  truth; the payload is the same data as trustworthy JSON for the model.
- The payload is **ephemeral**: it lives for exactly one tool result and is
  threaded to the next model turn. Nothing persists it.
- The payload is **opaque to the engine**: aish serializes it (`model_content`)
  and renders a fallback (`raw_body`) but never inspects, indexes, queries, or
  reshapes its contents.

### Out of scope — the non-goals (never build these)
- **No pipeline / composition engine.** No piping one tool's structured output
  into another tool as typed input. Tools do not chain through aish.
- **No query language over payloads.** No `jq` / JSONPath selectors, no
  `:select` / `:where` / `:map` verbs, no filter/transform operators.
- **No persistent typed-result store.** Payloads are per-call and ephemeral; no
  table of past results to address or join against.
- **No schema registry / typed-tool contract system.** The payload stays an
  opaque `serde_json::Value`. The engine declares no schemas and validates no
  shapes.

> **Boundary, in one line:** a tool may *describe* its result in a typed way;
> the system must never *operate* on those types as a programmable pipeline.

### Why this line (rationale)
- **aish's contract is "route, don't compute."** A line is either a real shell
  command or a request to the model. Adding typed operators would make aish a
  third thing — a dataflow runtime — competing with the shell it shells out to.
  That is `aish-next.md` §3.4's explicit non-goal.
- **The structured payload exists to make the MODEL smarter, not aish.** The
  win is the LLM parsing trustworthy structure instead of re-deriving it from
  alignment/ellipsis-corrupted ASCII. That win is fully captured by *passing*
  the JSON through. *Operating* on it adds engine surface, a query/þschema
  language to learn, and a maintenance burden — for a capability the model
  already has (it can reason over the JSON directly).
- **Opaque + ephemeral keeps the blast radius tiny.** Because the engine never
  inspects the payload, a new structured tool needs zero engine changes, and a
  bad payload can never corrupt aish state — it is just bytes the model reads
  once.

If a future need looks like it wants payload operators, that is a **new**
design conversation with its own PRD — not an incremental extension of S7.

## 4. Goals

- **G1** — both payload paths covered by deterministic unit tests (string-only +
  optional-structured) through the backend render, the model-facing
  representation, and the Ctrl-O raw path.
- **G2** — scope guardrail documented (this §3) with rationale + a one-line
  pointer from the code (`ToolResult` definition).
- **G3** — no new runtime surface; tests + docs only. Any bug fix is minimal and
  in scope.

## 5. Acceptance criteria

- **AC1** — tests cover the **string-only** path: a text-only `ToolResult`
  renders to each backend's wire format as today — **no** payload key, `content`
  verbatim, `is_error` honoured.
- **AC2** — tests cover the **structured** path: the payload reaches the
  model-facing representation (`model_content`) **and** is consistent with the
  Ctrl-O raw view (`raw_body`), while `content` stays correct — the payload is
  **additive**, never a substitute for `content`.
- **AC3** — scope guardrail documented in this file (§3) + a one-line pointer
  comment at the `ToolResult` definition + a CHANGELOG note.
- **AC4** — `cargo test` / `clippy` / `fmt` clean.

## 6. Verification

- `cargo test` green; removing either path's handling fails a test:
  - drop `model_content`'s structured branch → the additivity / compact-JSON
    tests fail;
  - let the payload leak onto the wire as a sibling key → the string-only
    wire-shape tests (`render_string_only_tool_result_wire_shape_has_no_payload_key`
    in `claude.rs` + `grok.rs`) fail on the exact-key-count assertion;
  - substitute the JSON for the human raw view → the `raw_body` additivity test
    fails.
- `cargo clippy` / `cargo fmt --check` clean.
- A reviewer can state the boundary from §3 and find it from the code pointer at
  the `ToolResult` definition.
