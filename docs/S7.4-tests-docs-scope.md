# PRD — S7.4 / TASK-142: Tests + docs; bound the scope (no pipeline engine)

> S7 gives aish tools a second, *typed* voice: alongside the human-readable
> `content` string, a tool may attach an optional structured payload that the
> model can reason over and the user can inspect raw (Ctrl-O). S7.4 is the
> sprint's closing card — it makes that capability **trustworthy and bounded**:
> tests that pin both payload paths, and a written guardrail that stops the
> feature from sliding into a structured-pipeline engine.

- **Task:** TASK-142 (`card_459128d4cc9e`)
- **Sprint:** aish-next S7 — Structured results & diagnostics (`sprint_ceae1c2263d6`)
- **Priority / size:** medium · 3 pts
- **Depends on:** S7.2 (TASK-140, typed `ToolResult` payload) and S7.3 (TASK-141,
  threading structured results to the model + raw-output rendering). S7.1
  (TASK-139, miette diagnostics) is parallel and not a hard dependency.

## 1. Problem

The S7 sprint introduces an optional structured payload on tool results:

- **S7.2** extends `backend::ToolResult` so a tool can return, in addition to the
  rendered `content` string, an optional typed/structured value (the machine
  representation of what the tool found).
- **S7.3** threads that structured value to the model and adds a raw-output
  (Ctrl-O) view so a human can see the untruncated, unformatted payload.

That leaves two open risks the sprint must close before the work is "done":

1. **Correctness is unpinned.** There are now *two* result paths — the legacy
   string-only path and the new structured-payload path — and nothing guarantees
   both keep working as the code evolves. A regression on either path is silent:
   the string path quietly drops the payload, or the structured path mangles the
   `content` the user sees.
2. **Scope is undefined.** "Tools can return structured data the model reasons
   over" is one inch away from "let's add operators to filter/transform/compose
   tool outputs" — i.e. reinventing a shell pipeline / query engine inside aish.
   That is an explicit non-goal (aish-next.md §3.4), but a non-goal that lives
   only in someone's head is a non-goal that gets violated in the next PR.

S7.4 exists to retire both risks: **lock the behaviour with tests, and write the
boundary down where the next contributor will read it.**

## 2. Goals

- **G1 — Both payload paths are covered by tests.** The string-only path and the
  optional-structured-payload path each have explicit, deterministic test
  coverage at the unit level, including the round-trip into the backend wire
  format and the raw-output rendering.
- **G2 — The scope guardrail is documented.** A clear, discoverable statement —
  "typed tool results only; never a structured pipeline/query engine" — lives in
  the repo (this PRD + a pointer from the code), with the rationale and the line
  that must not be crossed.
- **G3 — No new runtime surface.** S7.4 adds tests and docs only. It introduces
  no new tool, flag, config key, or wire-format change. If the tests reveal a
  bug in S7.2/S7.3 behaviour, the fix is minimal and in-scope; no new feature
  rides in on this card.

## 3. Non-goals (the guardrail itself)

These are the things S7.4 explicitly forbids — now and as a precedent:

- **No pipeline / composition engine.** aish will not grow operators to pipe one
  tool's structured output into another's input, nor a DSL to filter, map,
  reduce, join, or sort tool payloads. Composition is the *model's* job (it reads
  the structured result and decides the next tool call) or the *real shell's*
  job — not a new in-process engine.
- **No query language over payloads.** No JSONPath/jq-style selector surface, no
  `:select`/`:where` verbs, no saved-query objects.
- **No persistent typed-result store.** Structured payloads are per-call,
  in-memory, and ephemeral; they are not accumulated into a queryable dataset.
- **No schema registry / typed-tool contract system.** The payload stays an
  opaque-to-the-engine `serde_json::Value` (or equivalent); the engine does not
  validate it against per-tool schemas.

The boundary, stated once: **a tool may *describe* its result in a typed way; the
system must never *operate* on those types as a programmable pipeline.**

## 4. Acceptance criteria

From the card, made testable:

| # | Criterion | Met by |
|---|-----------|--------|
| AC1 | tests cover both payload paths | Unit tests exercising (a) a `ToolResult` with `content` only and (b) a `ToolResult` carrying the optional structured payload — each asserted through the backend render + the model-facing and Ctrl-O raw paths. |
| AC2 | scope guardrail documented | This PRD (`docs/S7.4-tests-docs-scope.md`) §3, plus a one-line pointer comment at the `ToolResult` definition referencing it, so the boundary is visible at the code that would be tempted to cross it. |

## 5. Approach

### 5.1 Tests (AC1)

Cover the two paths where they diverge, with table-style unit tests so adding a
case is cheap:

- **String-only path** — a `ToolResult` with no structured payload renders to the
  backend wire format exactly as today (no payload key emitted, `content`
  verbatim, `is_error` honoured). This is the regression fence for "structured
  support didn't change the default".
- **Structured path** — a `ToolResult` with a structured payload: assert the
  payload reaches the model-facing representation, the human-visible `content` is
  still correct, and the raw-output (Ctrl-O) view surfaces the untruncated
  payload.
- **Round-trip / equivalence** — the structured and string paths agree on what
  the user *sees*; the payload is additive, never a substitute for `content`.

Tests live next to the code they pin (`src/backend/mod.rs` and the S7.3 rendering
site), need no network or TTY, and run under `cargo test`.

### 5.2 Docs + guardrail pointer (AC2)

- This PRD is the canonical statement of scope and rationale.
- A short doc-comment at the `ToolResult` struct points here, so a contributor
  reaching for "let me add a filter operator on payloads" hits the boundary at
  the exact spot they'd extend.
- A line in `CHANGELOG.md` records the S7 structured-results capability and its
  bounded scope.

## 6. Verification

- `cargo test` green, with the new tests demonstrably exercising both paths
  (removing either path's handling makes a test fail).
- `cargo clippy` / `cargo fmt` clean.
- A reviewer can read §3 and the code pointer and state the boundary without
  asking anyone.

## 7. Risks & mitigations

| Risk | Mitigation |
|------|-----------|
| The guardrail is documented but later ignored. | Pointer comment at the code site + CHANGELOG note make the boundary load-bearing at review time, not just tribal knowledge. |
| Tests pin the wire format too tightly and become brittle. | Assert on observable behaviour (what the model sees / what Ctrl-O shows), not incidental serialization detail. |
| Scope-creep fix sneaks in under "tests revealed a bug". | G3: any fix must be minimal and in the S7.2/S7.3 behaviour already shipped; a genuinely new need becomes a fresh card. |

## 8. Out of scope (left as seams)

- Any future *opt-in* typed-tool contract system would be a separate, debated
  proposal — not a slippery extension of this card.
- miette-based diagnostic spans (S7.1/TASK-139) are tested under their own card.
