# S1.4 SPIKE — tokio reaper vs `waitpid(WUNTRACED)` coexistence

**Status:** decided · **Date:** 2026-06-12 · **Card:** TASK-111 · **Sprint:** aish-next S1

This is the gate for all of Phase 1. The output is a decision, not code.

## Question

aish currently runs every child through `tokio::process` (see
`src/tools.rs::run_program`, `src/tools.rs::spawn_background`,
`src/tools.rs::run_on_tty`, and `src/pipeline.rs::run`). Real job control —
the S2 deliverable: Ctrl-Z suspend, `fg`/`bg`, a `jobs` list that shows
*stopped* children — requires the parent to learn when a foreground child is
**stopped**, not just when it exits. That needs `waitpid(..., WUNTRACED)`.

`tokio::process` installs its own global, SIGCHLD-driven reaper. Can a manual
`waitpid(WUNTRACED)` job-control reaper coexist with it, or must foreground
exec move off `tokio::process` entirely (nix / command-group + a hand-written
reaper)?

## Verdict

**Keep `tokio::process`. Coexistence is achievable.** Foreground/interactive
exec gets a *self-managed* spawn + reaper; the captured, background, and
pipeline paths keep `tokio::process` unchanged.

**→ S1.5 (TASK-112) is sized at 3 SP, not 8.** The 5 SP of slack reallocates
to S2.

## Why coexistence works

The fear is the classic double-reap race: two reapers both call `waitpid` on
the same PID, one steals the exit status, and the other's wait hangs forever.
That race does **not** arise here, because the two reapers operate on
**disjoint PID sets**:

1. **tokio only reaps PIDs it owns.** `tokio::process`'s reaper, on each
   SIGCHLD, polls the children it spawned (its `Child` handles and its orphan
   queue) with `waitpid(pid, WNOHANG)` for each *known* pid. It does **not**
   `waitpid(-1)` to claim arbitrary children, and it does **not** pass
   `WUNTRACED` (so it never observes — and never consumes — a *stop*). A child
   spawned **outside** tokio is therefore invisible to tokio's reaper: tokio
   never calls `waitpid` on a pid it didn't create.

2. **aish reaps only its foreground pid.** If the foreground job is spawned via
   nix / command-group (not tokio), aish can `waitpid(fg_pid,
   WUNTRACED | WCONTINUED | WNOHANG)` on exactly that pid. No overlap with
   tokio's set ⇒ no stolen wait, no double reap.

3. **The one shared global is the SIGCHLD disposition — and it stays shared,
   not clobbered.** aish must **not** install a raw `sigaction(SIGCHLD)`; that
   would overwrite tokio's handler and break tokio's own child reaping.
   Instead, subscribe through `tokio::signal::unix::signal(SignalKind::child())`.
   That registers an *additional* listener on tokio's shared signal plumbing;
   multiple `Signal` streams for the same signal all receive every
   notification. So tokio's internal process reaper and aish's job-control
   reaper are both driven off the same SIGCHLD events without fighting over the
   handler.

Net: two reapers, disjoint PID sets, one shared signal source. They coexist.

## What S1.5 actually changes (the 3 SP)

Only the **foreground single-child path** moves; everything else is untouched.

1. **`run_on_tty` (src/tools.rs)** — used by both `run_interactive` and the
   REPL's direct dispatch — stops using `tokio::process::Command` and spawns
   via `command-group` (or raw `nix::unistd` fork/`setpgid`/`execvp`). This is
   what lets aish:
   - put the child in its **own process group** (`setpgid`) and make that group
     the terminal's foreground group (`tcsetpgrp`) — the prerequisite for
     Ctrl-Z / Ctrl-C to reach the *job* instead of aish;
   - detect a SIGTSTP **stop** via `waitpid(WUNTRACED)`, mark the job
     `Stopped`, restore aish as the terminal's foreground group, and return to
     the prompt;
   - resume on `fg`/`bg` with `SIGCONT` + `waitpid(WCONTINUED)`.

2. **A small reaper task** woken by a `tokio::signal` SIGCHLD stream that
   `waitpid`s the foreground pid with `WUNTRACED | WCONTINUED | WNOHANG` and
   updates job state.

3. **`tokio::process` is retained as-is** for the exit-only paths that never
   need stop detection: `run_program` (capture + timeout), `spawn_background`
   (background jobs), and `pipeline::run` (pipe wiring).

## Why this is 3 SP, not 8

8 SP was the "rip out `tokio::process` and write one unified manual reaper for
*every* exec path" outcome. We don't need that: tokio's owned-pid-only reaping
means the captured/background/pipeline code keeps working untouched alongside a
self-reaped foreground path. The change is one function (`run_on_tty`) plus a
contained reaper and the `tcsetpgrp`/process-group dance.

## Risks to validate during S1.5

- **SIGTTOU self-stop.** A process that isn't in the terminal's foreground
  group gets SIGTTOU when it calls `tcsetpgrp`. Wrap the `tcsetpgrp` dance with
  `SIGTTOU` ignored (standard job-control idiom).
- **command-group vs raw nix.** `command-group` gives clean process-group kill
  semantics, but confirm it does **not** install its own SIGCHLD reaper that
  would re-introduce the conflict. If it does, prefer raw `nix::unistd` +
  `nix::sys::wait::waitpid`.
- **Defensive assertion that tokio never `waitpid(-1)`s.** This verdict rests
  on tokio reaping only owned pids. Add an integration test in S1.5: spawn a
  non-tokio child, stop it (SIGTSTP), and assert (a) tokio-spawned children
  still reap normally and (b) the non-tokio child's stop/exit is observed
  *only* by aish's reaper. If a future tokio version regresses to `waitpid(-1)`,
  this test fails loudly.
- **Pipelines stay on the shared-group model for now.** `pipeline::run`
  currently relies on all stages sharing aish's foreground group so a terminal
  Ctrl-C hits them at once. Giving pipelines their own group for Ctrl-Z is S2
  polish, explicitly out of S1.5 scope (S1.5 = the single-foreground-child
  path).

## One-line summary

Keep `tokio::process`; give foreground exec a self-reaped
nix/command-group path driven off a shared `tokio::signal` SIGCHLD stream.
S1.5 = 3 SP; 5 SP of slack moves to S2.
