# PRD — S7.2: Optional typed/structured ToolResult payload (TASK-140)

- **Task:** TASK-140 · `card_02dc93ee8d5b`
- **Sprint:** SPR-048 — *aish-next S7 — Structured results & diagnostics*
- **Story points:** 5 · **Priority:** medium
- **Status target:** Plan → Analyze
- **Siblings:** TASK-139 (S7.1 miette diagnostics), **TASK-141 (S7.3 thread to model + Ctrl-O rendering)**, TASK-142 (S7.4 tests + docs / bound scope)

## 1. Summary

Give `ToolResult` an **optional** structured payload — typed JSON (records /
tables) alongside the human-readable `content` string — for the handful of
built-in tools whose output already *is* structured (`list_dir`, `glob_expand`,
`grep_files`, `stat_file`, `diff_files`, and the MCP passthrough, which is JSON
on the wire). The text rendering every tool produces today is unchanged; the
payload is purely additive metadata the model can trust instead of re-parsing
ASCII.

This is the **data-shape** half of S7. Threading the payload onto the wire and
the Ctrl-O raw-output rendering are TASK-141 (S7.3); this card lands the type,
the population, and the population's tests.

## 2. Problem & motivation

Every tool result is a `String` today:

```rust
pub struct ToolResult {
    pub id: String,
    pub content: String,
    pub is_error: bool,
}
```

For free-form program output that is exactly right — the LLM is a superb
universal text parser, which is the whole reason aish does **not** need a typed
pipeline. But a subset of tools emit output that is *already* tabular or
record-shaped (`list_dir` → name/type/size rows; `stat_file` → a field map;
`grep_files` → path:line:text triples). The model currently has to re-derive
that structure from the rendered text every time, which is:

- **lossy** — column alignment, truncation, and ellipsis can corrupt a value;
- **wasteful** — re-parsing a table the tool already had in hand;
- **fragile** — a width tweak to the human rendering silently changes what the
  model parses.

Where the structure is **cheap** (the tool already holds the typed values before
it formats them), handing the model JSON it can trust is a low-cost, high-trust
win.

## 3. Goals

| # | Goal |
|---|------|
| G1 | Add an **optional** `structured` payload to `ToolResult` that carries typed JSON for structured-emitting tools. |
| G2 | Populate it for the tools whose data is already structured **at the point of formatting**, where it costs effectively nothing (`list_dir`, `glob_expand`, `grep_files`, `stat_file`, `diff_files`). |
| G3 | Leave **text-only** tools (`run_program`, `read_file`, `escalate`, …) completely unchanged — `structured` stays `None`. |
| G4 | Keep `content` (the rendered text) the **source of truth** and always present; the payload is additive, never a replacement. |
| G5 | Zero behaviour change on the wire **in this card** — the field exists and is populated but threading/rendering is TASK-141. |

## 4. Non-goals (scope guardrails)

> The task description is explicit: *"Deliberately NOT a structured pipeline
> engine — the LLM is the universal text parser nushell built to avoid."*

- **NG1 — No pipeline engine.** No typed values flowing tool→tool, no `where`/
  `select`/`sort` operators, no schema negotiation. aish stays a text shell.
- **NG2 — No mandatory schema.** `structured` is `Option<Value>`; there is no
  per-tool typed struct contract the model or tools must satisfy.
- **NG3 — No payload for free-form output.** `run_program` stdout, file
  contents, and narrative tool results stay text-only — forcing JSON onto them
  would be the exact re-structuring nushell built to avoid.
- **NG4 — No new tools.** This adds a field and populates it; it does not add or
  rename tools.
- **NG5 — No wire/threading/rendering changes** (TASK-141) and **no new
  tests-as-docs / scope writeup** (TASK-142) beyond this PRD.

## 5. Current state

- `ToolResult` (`src/backend/mod.rs:58`) — three fields, all text/bool.
- Constructed in `tools::execute` (`src/tools.rs`) from a tool's
  `Result<String>`, and in a handful of synthetic sites (`engine.rs`
  loop-guard/replay results, `turn_audit.rs`, `worker_store.rs`, `grok.rs`,
  `context.rs`).
- Structured-emitting tools (`list_dir`, `glob_expand`, `grep_files`,
  `stat_file`, `diff_files`) build typed Rust values, then `format!` them into
  the returned `String`. The typed values are discarded after formatting — that
  discard is the cheap win this card reclaims.
- The persisted worker transcript and turn-audit journal record
  `(content, is_error)`; neither needs the payload (it is a model-facing
  optimization, not part of the resume contract).

## 6. Proposed design

### 6.1 Type change

```rust
/// The result we feed back for one tool call.
#[derive(Debug, Clone)]
pub struct ToolResult {
    pub id: String,
    pub content: String,
    pub is_error: bool,
    /// Optional typed payload for tools whose output is already structured
    /// (records / tables). `content` stays the rendered, human-readable source
    /// of truth; this is additive JSON the model can consume without
    /// re-parsing the text. `None` for free-form / text-only tools — by design
    /// (this is NOT a typed pipeline; see the S7.2 PRD non-goals).
    pub structured: Option<serde_json::Value>,
}
```

- `Default`-friendly: every existing constructor sets `structured: None`. To
  minimize churn across the ~10 synthetic construction sites, add a small
  constructor surface:
  - `ToolResult::text(id, content, is_error)` → payload `None` (the existing
    behaviour, used everywhere today);
  - `ToolResult::structured(id, content, value, is_error)` → carries the
    payload.
- `execute`'s success arm wraps the tool's return so a tool can opt in. Two
  candidate shapes (decide in Analyze):
  - **(a)** widen the internal tool signature to return
    `(String, Option<Value>)` for the structured tools and keep `Result<String>`
    elsewhere via a `From`; or
  - **(b)** keep `Result<String>` and have each structured tool stash its
    payload on a scratch field / return a small enum. (a) is cleaner; (b) is
    smaller-diff. **Recommendation: (a)** for the five structured tools, behind
    a helper so the text tools are untouched.

### 6.2 Per-tool payloads (the "where cheap" set)

| Tool | Payload shape (illustrative) | Cost |
|------|------------------------------|------|
| `list_dir` | `[{ "name", "type": "file\|dir\|symlink", "size": <bytes> }]` | free — already iterated |
| `glob_expand` | `[{ "path", "type", "size" }]` | free |
| `grep_files` | `[{ "path", "line": <n>, "text" }]` | free |
| `stat_file` | `{ "type", "size", "perms": "0644", "uid", "gid", "nlink", "modified", "symlink_target"? }` | free |
| `diff_files` | `{ "identical": bool, "hunks": [{ "header", "added": <n>, "removed": <n> }] }` (or minimally `{ "identical": bool }`) | cheap |
| MCP (`mcp__*`) | the tool's JSON response when it already returns JSON | free — re-attach the parsed value |

`content` for each stays byte-for-byte what it is today.

### 6.3 What stays `None`

`run_program`, `run_interactive`, `read_file`, `write_file`, `edit_file`,
`copy_file`, `rename_file`, `append_file`, `change_dir`, `remember`, `recall`,
`job_output`, `run_in_background`, `background_status`, `tell`, `escalate`,
`get_skill`, and every loop-guard / replay / declined synthetic result.

## 7. Acceptance criteria

- **AC1 (card AC):** structured-emitting tools carry typed data; text tools
  unchanged. → `list_dir` / `glob_expand` / `grep_files` / `stat_file` /
  `diff_files` set `structured = Some(..)`; all other tools leave it `None`.
- **AC2:** `content` (rendered text) is identical to today for every tool — no
  diff in human-facing output.
- **AC3:** the payload, when present, is valid JSON whose values match the
  rendered text (no divergence between table and JSON).
- **AC4:** all existing `ToolResult` construction sites compile and behave
  unchanged (payload defaults to `None`).
- **AC5:** no wire/threading/rendering change in this card; `Backend::complete`
  inputs are unaffected (that is TASK-141).
- **AC6:** unit tests assert payload presence + shape for the structured tools
  and **absence** for a representative text tool.

## 8. Testing

- Per-tool unit tests in `tools.rs` (`fileops_tests` already exercises these
  tools) extended to assert `result.structured`:
  - `list_dir` / `glob_expand` → array of objects with `name`/`path` + `type` +
    `size`.
  - `grep_files` → objects with `path` + `line` + `text`; honours `glob` scope.
  - `stat_file` → object with `type` + `size` + `perms`.
  - `diff_files` → `identical` flag flips correctly; inline `b_content` path
    covered.
  - a text tool (`read_file` or a `run_program` echo) → `structured == None`.
- `cargo test --no-default-features` (the CI gate) stays green.

## 9. Risks & mitigations

| Risk | Mitigation |
|------|-----------|
| Payload drifts from rendered text over time | Build both from the **same** typed values in one place per tool; AC3 test pins parity. |
| Scope creep toward a pipeline engine | Non-goals NG1–NG3; the field is `Option`, never consumed tool→tool. |
| Construction-site churn across ~10 sites | `ToolResult::text(..)` constructor keeps the common path a one-line change; `#[derive(Default)]`-style ergonomics. |
| Token cost of duplicating data (text + JSON) to the model | Out of scope here; TASK-141 decides *when* to send the payload (e.g. only on Ctrl-O / only structured tools) so cost is controlled at the threading layer. |
